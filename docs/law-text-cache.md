# 法令本文キャッシュの動作

この文書は、ブラウザ上で法令本文を再利用するためのキャッシュの仕組みをまとめたもの。実装は `app.js` にある。

## 1. 目的

同じ法令を再度開いたときに、法令本文API（`/api/2/law_data/`）への再取得を避け、表示を速くする。キャッシュの単位は法令IDではなく**法令履歴ID（revision ID）**。法令IDで開いた場合も、インデックス経由で「いま施行中の最新履歴」のキャッシュを探す。

## 2. 保存場所

| 種類 | 場所 | キー / 名前 | 中身 |
|---|---|---|---|
| 本文 | Cache Storage | `law-text-cache-v1` | 法令本文APIのJSONレスポンス。リクエストURLは履歴ID付きの `law_data` URL |
| 最新履歴インデックス | `localStorage` | `law-latest-revision-index` | `{ [法令ID]: 履歴ID }` |
| 閲覧履歴 | `localStorage` | `law-view-history` | 直近閲覧した履歴IDの一覧（最大15件） |
| 固定一覧 | `localStorage` | `law-pinned-laws` | ユーザーが固定した履歴IDの一覧 |

Cache Storage が使えない環境では、キャッシュの読み書きをスキップして常にネットワーク取得する。インデックス・履歴の `localStorage` 失敗も無視し、閲覧自体は続行する。

## 3. 本文の読み取り（`fetchLawData`）

`?id=` に渡された値が履歴IDか法令IDかで分岐する。履歴IDかどうかは、値に `_` が含まれるかで判定する。

### 履歴IDで開いた場合

1. Cache Storage に、その履歴IDの `law_data` URL があるか調べる
2. あればそれを返す（cache hit）
3. なければネットワーク取得し、成功レスポンスを**その履歴IDのURL**で `cache.put` する

### 法令IDで開いた場合

1. `localStorage` のインデックスから、その法令IDに対応する最新履歴IDを読む
2. 履歴IDが分かり、かつその本文が Cache Storage にあればそれを返す
3. インデックス未登録、または本文が無い場合はネットワーク取得する
4. 取得成功時、レスポンスの `revision_info.law_revision_id` で Cache Storage に保存する

`fetchLawData` は**インデックスを更新しない**。本文の保存だけを行い、どの履歴が「最新」かの判定は改正履歴側に任せる。

## 4. 最新履歴インデックスの更新（`loadAmendmentHistory`）

法令ページ表示後、改正履歴API（`/api/2/law_revisions/{law_id}`）を常に取得する（`law_info.law_id` がある場合）。ここでインデックスを更新する。

最新の判定は `findLatestRevision` による。

- `amendment_enforcement_date` があり、かつ今日（`Asia/Tokyo` の暦日）以前の履歴だけを候補にする
- その中で施行日が最も新しいものを選ぶ
- 施行日が同じなら `law_revision_id` の文字列比較で大きい方を選ぶ
- 施行済み候補が一件も無い場合は、APIが返した先頭の履歴にフォールバックする

選ばれた履歴IDを `setIndexedLatestRevision(lawId, revisionId)` でインデックスに書く。これがインデックスの唯一の書き込み経路である。

### 法令IDで開いたときのずれ検知

リクエストが法令IDであり、表示中の履歴IDとインデックス上の最新履歴が異なる場合、確認ダイアログを出す。

- ユーザーが再読み込みを選ぶと `location.reload()` する
- この時点でインデックスはすでに新しい履歴IDを指しているため、再読み込み後はキャッシュミスならネットワークから最新本文を取り、ヒットすればその本文を出す

改正履歴の取得に失敗した場合、インデックスは更新されない。次回もキャッシュミスまたは古いインデックスのままになり得るが、表示自体は可能で、最適化を逃すだけである。

## 5. 典型的な流れ

### 初回訪問（法令ID）

1. インデックス無し → ネットワークで本文取得 → 履歴IDで Cache Storage に保存
2. 改正履歴取得 → 最新施行履歴をインデックスに登録
3. 2回目以降の同法令ID訪問は、インデックス経由で cache hit になる

### 2回目以降（法令ID、インデックスあり）

1. インデックスの履歴IDで Cache Storage を参照して即表示
2. 裏で改正履歴を取得し、インデックスを最新に更新
3. 表示中より新しい施行履歴があれば再読み込みを確認する

### 履歴IDで直接開く

1. その履歴の Cache Storage を参照（あれば hit、なければ取得して保存）
2. 改正履歴取得時も、インデックスは「法令全体の最新施行履歴」に更新される（表示中の履歴そのものとは限らない）

## 6. キャッシュの削除（`trimUnusedCache`）

Cache Storage のエントリは、固定一覧と閲覧履歴に含まれる履歴IDだけ残し、それ以外を削除する。

実行タイミング:

- 閲覧履歴から一件削除したとき
- 閲覧履歴が上限（`MAX_VIEW_HISTORY = 15`）を超えて古い件が落ちたとき

固定一覧から外しただけではトリムしない。履歴にも残っていれば本文キャッシュは残る。

インデックス（法令ID → 履歴ID）はトリム対象外。指している本文が既に削除済みなら、次回はキャッシュミスとしてネットワーク取得する。

## 7. 閲覧履歴との関係

`rememberLaw` は**履歴ID**を閲覧履歴に保存する（法令IDではない）。これにより、キャッシュの保持キーと履歴・固定のIDが一致する。履歴タイトルには施行日があれば付与する（`formatRevisionTitle`）。

## 8. 意識しておく境界

- 検索APIや改正履歴APIのレスポンスはキャッシュしない。キャッシュ対象は法令本文のみ
- 未来施行の履歴は「最新」としてインデックスに載せない（施行日が今日以前のものだけ）
- `Caches` API 非対応環境では常にネットワーク取得になる
- インデックスの更新失敗や改正履歴API失敗は、次回の再取得で吸収する想定で、致命的エラーにはしない
